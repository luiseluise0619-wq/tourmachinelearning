# 과제 9 공식 스펙 정렬 — FestCast 커버리지

> 출처: 2026 관광데이터 활용 공모전 ②-2 웹·앱 구현 부문 지정과제 참고자료(프롬프톤 수상작 기반).
> ⚠️ 공식 안내: **1차 심사 시 "해시태그와 연관된 기능 구현 내용"으로 기능설명서 작성 요청** 예정.
> → **해시태그 = 채점 기준.** 아래는 우리 구현이 각 요구를 어떻게 커버(+초과)하는지 매핑.

## 과제 9 공식 정의

- **해결과제**: 축제 수요 예측 실패 및 주관적 경험 의존형 기획으로 인한 예산 낭비 리스크,
  대규모 관광객 쏠림에 따른 축제 만족도 저하
- **① 서비스명(예시)**: 축제 흥행 예보 서비스 → **우리: FestCast(페스캐스트)** ✅ 일치
- **② 타깃**: 축제 예산 집행 전 기획안의 객관적 검증이 필요한 **지자체·축제 위탁사 실무자**
- **③ 주제**: 축제의 **사전 흥행 가능성을 예측·진단하는 예보** 서비스
- **④ 기능(요구)**
  1. 개최 축제 개요 및 프로그램 세부 계획 항목 **입력 기능**
  2. 데이터 기반 **흥행도 도출** + **기획 보완 피드백 리포트** 추천 기능
- **해시태그**: `#축제/행사 기획` `#사전 수요 예측` `#보완 피드백 제공` `#데이터 기반`

## 커버리지 매핑 (요구 → FestCast)

| 해시태그(채점기준) | 요구 기능 | FestCast 구현 | 상태 |
|--------------------|-----------|---------------|------|
| **#축제/행사 기획** | 기획안(개요·프로그램) 입력 | `FestivalPlan`/`RegionContext` 등 입력 스키마 완비 | 🟡 UI 필요 |
| **#사전 수요 예측** | 예상 방문자·흥행도 | 흥행도(5요인) + **100명 단위 확률예보** + 내/외국인 분리 | 🟢 초과 |
| **#보완 피드백 제공** | 기획 보완 리포트 | `generate_feedback` — 약점별 what-if 처방(13종) | 🟢 초과 |
| **#데이터 기반** | 데이터 근거 | 실측 1,266건 + 회귀 계수·p값 근거체계 | 🟢🟢 강점 |

## 우리가 공식 예시를 초과하는 지점 (차별점)

공식 예시는 "입력 → 흥행도 → 피드백"의 기본형. FestCast는 여기에:

- **확률 예보 + 쏠림 위험** — 단일 숫자 아닌 분포 + 수용초과 확률
  → 과제 9 후반부 "**대규모 관광객 쏠림·만족도 저하**"를 직접 해결 (예시엔 없음)
- **내국인/외국인 분리 + K콘텐츠 효과** — 주최(관광공사)의 방한 외국인 유치 미션 정조준
- **마케팅 추천** — 주변 인구 기반 타깃·채널·프로그램
- **근거 체계(T1/T2/T3)** — 계수·p값·SHAP로 "왜 이 예측인가"를 방어
  → `#데이터 기반` 해시태그를 가장 깊게 충족

## 유일한 실질 갭

- 🟡 **기획안 입력 UI(동작 데모)** — 엔진·데이터·근거는 완비. 실무자가 실제로 입력하는
  화면이 아직 없다. 기능①(입력 기능)을 눈에 보이게 하려면 데모가 필수.
  → 업로드된 앱(지도·실데이터·배포) + FestCast 엔진 결합으로 해결 가능.

## 기능설명서 대비 체크리스트

1차 심사 기능설명서는 **해시태그별 기능**으로 작성 요청됨. 각 해시태그에 대해:
- [ ] #축제/행사 기획 → 입력 화면 캡처 + 입력 항목 설명
- [x] #사전 수요 예측 → 흥행도·확률예보 산출 로직(`scoring.py`) + 검증(머드 오차 6%)
- [x] #보완 피드백 제공 → what-if 피드백 생성 로직 + 예시 리포트
- [x] #데이터 기반 → 데이터 출처(문체부·TourAPI·기상청) + 근거(회귀 계수·p값)

> 결론: 알맹이(예측·피드백·근거)는 채점기준을 **초과 충족**. 남은 건 입력 UI(데모)뿐.
